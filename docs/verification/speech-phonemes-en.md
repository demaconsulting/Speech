# SpeechPhonemesEn System Verification

This document describes the verification design of the SpeechPhonemesEn system.

## Verification Approach

SpeechPhonemesEn is verified through its public API (`EnglishPhonemizer` and the two renderers) with the real embedded
data, by system tests in `test/DemaConsulting.Speech.Phonemes.En.Tests/SpeechPhonemesEnTests.cs`, and by FileAssert
tests of the built package. Where a test needs the text analysis (the golden corpora, the analyzed-text scenario) it
runs the real `EnglishTextAnalyzer` of SpeechTextEn on the sentence and hands its annotations to the phonemizer, exactly
as a model package does; where it needs a controlled annotation it supplies one directly. Nothing is mocked: the
dictionary, the reading tables, the letter-to-sound model and the renderers are the shipped ones.

The evidence is of three kinds:

- **Golden corpora**: about 150 own-written sentences (numbers, dates, times, currency, acronyms, contractions,
  possessives, hyphenation, heteronyms, unknown words, punctuation and unsupported symbols) with the reviewed word
  stream, and one reviewed sentence for each of the 395 reading ids. The expected columns are generated by the tools
  command `regenerate-goldens` and then reviewed line by line, so a changed line is a reviewed behavior change; a wrong
  line is fixed in the code, never accepted into the golden
- **Behavior scenarios**: short, readable system tests for each requirement (priority order, derived forms, unknown
  words, unsupported text, weak forms, long text, determinism)
- **Package inspection**: FileAssert tests of the built `.nupkg` for the license files, the public API surface and the
  absence of an inference-runtime dependency

The package data is also verified by the tools project's `--check` commands (`build-lexicon`, `train-lts`,
`propose-readings`), which rebuild or re-verify the embedded images and tables from the pinned dictionary; they need the
pinned download and therefore run on a developer machine or in a job that has fetched it. They are build-level gates,
not requirements evidence. The renderers' agreement with espeak-ng and misaki is measured locally and recorded as
aggregate numbers in `docs/evaluation/phonemes-en/`; no engine output is committed.

## Test Environment

- **Framework**: xUnit v3 running under the .NET SDK, on every target framework of the library
- **Execution**: `dotnet test` invoked by `build.ps1` and the CI pipeline; the FileAssert tests (`dotnet fileassert`)
  run after the packages are built
- **Project**: `test/DemaConsulting.Speech.Phonemes.En.Tests`
- **Files**: the golden files in `TestData` (`sentences-golden.tsv`, `readings-golden.tsv`, `oov-golden.tsv`,
  `piper-ipa-golden.tsv`, `kokoro-misaki-golden.tsv`), the committed form table of the reading inventory and gap list, a
  trimmed copy of the Piper voice's configuration (its symbol table) and Kokoro's own tokenizer file, all copied beside
  the test assembly; no test needs network access or a model
- **Isolation**: every test creates its own phonemizer or uses the immutable shared data; the determinism test uses its
  own threads

## Acceptance Criteria

A system test passes when the phonemizer and the renderers produce exactly the reviewed values and the properties named
in the scenarios hold. The system passes verification when every scenario below passes on every target framework and the
FileAssert tests pass on a built pre-release package (a stable version builds no package and the tests then have nothing
to inspect).

## Test Scenarios

### Dictionary pronunciation

**Tests**: `SpeechPhonemesEn_Phonemize_DictionaryWords_UseTheDictionaryPronunciation`,
`SpeechPhonemesEn_Phonemize_NoAnnotations_EveryInventoryFormGetsItsDefaultReading`

`Cat RECORD don’t` gives the dictionary's own pronunciations (the first variant of `record`, the typographic apostrophe
accepted, any case) with the source `Lexicon` and nothing reported; without annotations every spelling of the reading
inventory that the dictionary lists is pronounced as the first variant of its entry.

### Readings

**Tests**: `SpeechPhonemesEn_ReadingGolden_EveryReadingIsPronouncedAsReviewed`,
`SpeechPhonemesEn_ReadingGolden_ClassifierHitRate_MeetsTheGate`,
`SpeechPhonemesEn_Render_EveryHeteronymReading_BothVoicesRenderTheChosenPronunciation`

Each of the 395 reading ids has one reviewed sentence; the pronunciation of the target word comes out of the pipeline
with the reading applied, end to end where the real classifier labels the sentence as intended and with the reading
forced where it labels it differently (the golden is not bent to the classifier). At least 95 percent of the sentences
are labeled correctly by the classifier today (97.5 percent measured), and the rows marked as classified end to end are
re-checked. The same 395 sentences prove that both voices say the chosen reading: the target word as rendered in its
sentence by the Piper renderer and by the Kokoro renderer (both with function-word tables on) equals what that renderer
renders for the pronunciation the reading table gives for the reading, on its own (the Piper voice may add the linking
r), so a rule of one voice that replaces or changes the reading of a heteronym is caught.

### Source priority

**Test**: `SpeechPhonemesEn_Phonemize_SourcesInPriorityOrder_OverrideReadingLexiconMorphologyLetterToSound`

One text with a host override on one word, a reading on the next, a dictionary word, a derived word and an unknown word
reports the sources `Override`, `Reading`, `Lexicon`, `Morphology`, `LetterToSound` in that order, which is the order of
the enumeration, and the override and the reading give their own pronunciations.

### Morphology

**Test**: `SpeechPhonemesEn_Phonemize_InflectedAndPrefixedWordsAbsentFromTheDictionary_AreDerivedFromTheirStem`,
`SpeechPhonemesEn_Phonemize_WordsEndingInNg_SpeakTheVelarStopOnlyWhereEnglishDoes`

Three words that are not dictionary entries (`unfollowed`, `unfollows`, `unfollow`) are derived by the morphology rules,
are not reported as out of vocabulary, and end in the sound the rule gives (`D` for the past, `Z` for the third person).
The comparatives and superlatives of `long`, `strong` and `young` speak the velar stop (`S T R AO1 NG G ER0` for
`stronger`, although the dictionary lists it first without the `G`), `singer`, `singing`, `longing` and `hanger` do not,
and `wrongest`, which the dictionary lacks, is derived with the stop.

### Out of vocabulary

**Test**: `SpeechPhonemesEn_Phonemize_UnknownWord_IsPronouncedByTheModelAndReported`

`Welcome Zorblax and Kathmandu`: the dictionary word is not reported; the two unknown words have phones, the source
`LetterToSound` and the out-of-vocabulary flag, and are listed in the result in order.

### Annotations from the text analysis

**Tests**: `SpeechPhonemesEn_Phonemize_AnalyzedText_SpeaksNormalizationsSpelledLettersAndReadings`,
`SpeechPhonemesEn_SentenceGolden_EverySentenceProducesItsReviewedWordStream`,
`SpeechPhonemesEn_Render_PhoneNumber_PausesBetweenItsDigitGroups`

`Dr. Smith paid $5 for the FBI record.` through the real analyzer gives `Doctor` and `five` as words, `FBI` as three
spelled letters with the letter names `EH1 F`, `B IY1`, `AY1` and the noun reading of `record`. Every sentence of the
golden corpus produces exactly its reviewed word stream (text, ARPAbet, punctuation, unsupported tokens and
out-of-vocabulary marks). `Please call 555-0147 before noon.` is read `five five five`, a pause, `zero one four seven`
(a comma for Piper, a dash for Kokoro), as are `(555) 014-7000` and `1-800-555-0147` group by group, and no hyphen stays
inside a word.

### Unsupported text

**Test**: `SpeechPhonemesEn_Phonemize_UnsupportedText_IsKeptAndReportedNeverDropped`

`Hi 😀 there, 日本.` keeps every word, mark and unsupported run as an item in order and lists the emoji and the Japanese
word as unsupported.

### Voice symbols

**Test**: `SpeechPhonemesEn_Render_SentenceCorpus_UsesOnlySymbolsOfTheVoiceModels`

Every sentence of the corpus renders, for both voices, to a non-empty string whose every symbol is in the Piper
`phoneme_id_map` or the Kokoro vocabulary respectively. The exhaustive version of this check (every dictionary
pronunciation, every sequence of three phones) is a subsystem scenario.

### Weak forms

**Tests**: `SpeechPhonemesEn_Render_FunctionWords_AreWeakForPiperAndFullForKokoroByDefault`,
`SpeechPhonemesEn_Render_FunctionWordAfterAVoicingAlternatingWord_KeepsItsFullForm`,
`SpeechPhonemesEn_Render_PronounIAfterAComma_KeepsAnAudibleVowelInTheKokoroRendering`

`a cup of the tea` renders for Piper as `ɐ kˈʌp ʌvðə tˈiː` (the article reduced, `of the` one unstressed group), keeps
the stress of `of` with weak forms off, and keeps the stress for Kokoro by default but not when weak forms are switched
on. `The shop is close to the station.` keeps the full `to` (`klˈOs tˈu ðə` for Kokoro, `klˈoʊs tˈuː ðə` for Piper)
while `She went to the station` keeps the reduced `tə`; the same holds after `excuse`, `house` and `use`.
`Honestly, I couldn't`, `So, I think so.` and `Well, I am here.` render `ˌI` (secondary stress) in the weak-form Kokoro
text and `ˈI` in the full-form one.

### Long text

**Test**: `SpeechPhonemesEn_Render_LongText_IsSplitAtClauseBoundariesWithinTheLimit`

Forty sentences render, for both voices, as several parts of at most 200 symbols each, every part but the last ending at
a clause mark, and together containing every sound of the whole rendering.

### Determinism

**Tests**: `SpeechPhonemesEn_Pipeline_RepeatedAndConcurrentRuns_GiveIdenticalResults`, and the golden tests above on
every target framework

Forty sentences phonemized and rendered by fresh phonemizers on many threads at once give exactly the strings of a
single-threaded run; the identity across runtimes is shown by the same golden passing on every target framework.

### Package license files and public API

**Tests**: `PhonemesEn_PackageLicenseFiles_Content`, `PhonemesEn_PackagePublicApi_Surface` (FileAssert)

The `.nupkg` carries `PACKAGE-LICENSE.md` starting with `SPDX-License-Identifier: MIT AND LicenseRef-CMUdict` and naming
`THIRD-PARTY-NOTICES.md`, the notices with the CMUdict copyright and the names of the embedded resources, and a nuspec
that names the license file; the generated API documentation lists exactly the nine public types and nothing of the
lexicon, letter-to-sound or reading internals; the nuspec has no ONNX or sherpa dependency.
